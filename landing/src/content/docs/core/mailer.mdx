The project uses `@nestjs/mail` with HTML templates. Emails are sent from the `EmailService`, which is called by the mail queue processor.

## Configuration

`mail.config.ts` holds the sender and transport selection. `EmailModule` registers the global `MailModule` asynchronously: the factory builds the transport from the config, points the `FileTemplateEngine` at `src/common/modules/email/templates/`, and fails at startup on a bad `MAIL_TRANSPORT` or missing credentials.

```typescript title="src/common/modules/email/email.module.ts"
MailModule.forRootAsync({
  inject: [mailConfig.KEY],
  useFactory: (config) => ({
    transport: mailTransport(config),
    templates: new FileTemplateEngine({
      dir: join(import.meta.dirname, 'templates'),
      cache: process.env.NODE_ENV === 'production',
    }),
    from: config.from,
  }),
})
```

The transport is picked by `MAIL_TRANSPORT`:

- `file` (default) — writes each mail to an `.eml` file under `MAIL_DIRECTORY` (`var/mail`) instead of sending it. For development.
- `smtp` — sends via `SMTP_URL` (e.g. `smtp://user:password@smtp.example.com:587`) with pooled connections.
- `resend` — sends via the Resend API with `RESEND_API_KEY`.

## Templates

The starter includes two HTML templates:

- `verification.html` — Renders the email verification OTP code.
- `password-reset.html` — Renders the password reset token.

Values go between double braces and are HTML-escaped. Place new templates in the same folder and reference them by name from a mail class. Templates are shipped to `dist` via the `*.html` asset entry in `nest-cli.json`.

## Mail classes and EmailService

Each mail is a typed `Mailable` provider. The class declares its data as an interface, and `render()` turns that data into a subject plus a body — either a template name with its context, or inline HTML built with the `html` tag (interpolated values are escaped):

```typescript title="src/common/modules/email/verification.mail.ts"
import { Injectable } from '@nestjs/common';
import type { Mailable } from '@nestjs/mail';

export interface VerificationMailData {
  code: string;
}

@Injectable()
export class VerificationMail implements Mailable<VerificationMailData> {
  render({ code }: VerificationMailData) {
    return {
      subject: 'Email Verification',
      template: 'verification', // src/common/modules/email/templates/verification.html
      context: { code }, // the values the template reads
    };
  }
}
```

```typescript title="src/common/modules/email/generic.mail.ts"
import { Injectable } from '@nestjs/common';
import { html, type Mailable } from '@nestjs/mail';

export interface GenericMailData {
  subject: string;
  body: string;
}

@Injectable()
export class GenericMail implements Mailable<GenericMailData> {
  render({ subject, body }: GenericMailData) {
    return {
      subject,
      html: html`<p>${body}</p>`, // ${body} is HTML-escaped
    };
  }
}
```

A few rules worth knowing:

- **Keep logic in `render()`, not the template.** The template engine is logic-less (values, `#if`/`#unless`, `#each`, partials) with no helpers or expressions. Format prices, build links, and translate strings in TypeScript, where they are typed and tested.
- **`render()` takes a second argument** with the send's `locale` and the parsed `to` recipients (`render(data, { locale, to })`). The starter does not use locales yet, but a mail class can read `locale` to translate its subject or pick locale-specific formatting.
- **Mail classes are injectable.** Register them in `EmailModule`'s `providers` so they can inject other providers (a repository, `ConfigService`) when a mail needs more than its `data`.
- **The `data` type is checked at send time.** `mailer.send(VerificationMail, { to, data })` requires `data: { code: string }` — a wrong shape is a compile error.

`EmailService` is the only caller most code needs. It sends each class through the global `Mailer` and exposes three methods:

```typescript
await this.emailService.sendEmail(to, subject, body);
await this.emailService.sendVerificationEmail(to, code);
await this.emailService.sendPasswordResetEmail(to, token);
```

For example, `sendVerificationEmail` calls `mailer.send(VerificationMail, { to, data: { code } })`. The service logs success and errors. If the mailer throws, the error propagates and the queue processor's retry logic decides whether the job is retried.

## Adding a new mail

1. Create a new `.html` file under `src/common/modules/email/templates/`.
2. Add a `Mailable` class whose `render()` returns the subject, template name, and context, and register it in `EmailModule`.
3. Add a method in `EmailService` that calls `mailer.send` with the new class.
4. Add a new job name and processor handler if the email is sent via the queue.

## Testing

Override the `MailTransport` with `InMemoryMailTransport` and read what was sent:

```typescript
const mailbox = new InMemoryMailTransport();
await Test.createTestingModule({ imports: [AppModule] })
  .overrideProvider(MailTransport)
  .useValue(mailbox)
  .compile();

const mail = mailbox.assertSent({ to: 'ada@example.com', mail: VerificationMail });
```

## Testing locally

With the default `file` transport, no SMTP setup is needed: register a user or request a password reset and open the `.eml` files in `var/mail` with any mail client. Set `MAIL_TRANSPORT=smtp` with a real `SMTP_URL` (or a test service such as Mailpit, Mailtrap, or Ethereal) when you want real delivery.
